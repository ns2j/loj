# LOJ

LOJ is a helper library for LibreOffice programming with Java.

LibreOffice provides the powerful [UNO API](https://api.libreoffice.org/), but using UNO directly from Java often requires many interfaces, `UnoRuntime.queryInterface()` calls, property operations, and connection-management code.

LOJ provides utilities and generated proxy classes that make LibreOffice objects easier to use from ordinary Java code.

In particular, it provides higher-level abstractions for Calc such as documents, sheets, ranges, and cells.

## Overview

LOJ consists of the following modules:

### loj-util

Utilities for connecting Java applications to LibreOffice.

It includes:

- LibreOffice process management
- Socket connections
- Pipe connections
- Connection pooling support
- Java / UNO stream conversion
- Temporary LibreOffice user directory support

### loj-proxy

A source-code generator for creating Java wrapper classes from LibreOffice UNO interfaces.

UNO programming often requires code such as:

```java id="vmtjgg"
XSomething xSomething =
    UnoRuntime.queryInterface(XSomething.class, object);

xSomething.someMethod();
```

`loj-proxy` generates wrapper classes that hide much of this interface-conversion code.

Generated classes include:

```text id="gmppxu"
P_Doc
P_Sheet
P_Range
P_Cell
P_Chart
...
```

The UNO interfaces used to generate each proxy are defined in `proxy.properties`.

### loj-sb-sample

A Spring Boot sample application demonstrating how to use LOJ.

It contains:

- Generated `loproxy` classes
- Higher-level Calc classes
- Spreadsheet manipulation examples
- Styles
- Charts
- Sheet copying and importing
- Document export
- LibreOffice connection pooling

## Architecture

The basic architecture is:

```text id="zqnpkl"
Application / Spring Boot
          |
          v
 Doc / Sheet / Range / Cell
          |
          v
 Generated P_* classes
      (loproxy)
          |
          v
 LibreOffice UNO API
          |
          v
 Socket / Pipe connection
          |
          v
     LibreOffice
```

LOJ separates automatically generated UNO wrappers from higher-level, handwritten Java APIs.

For example:

```text id="qapwzo"
UNO XSpreadsheet
       |
       | loj-proxy
       v
    P_Sheet
       |
       | extends
       v
     Sheet
```

`P_Sheet` contains the mechanical UNO interface delegation, while `Sheet` provides convenient spreadsheet operations.

## Generating the proxy classes

The `P_*.java` classes under `loproxy` are generated by `loj-proxy`.

This is particularly useful when upgrading the LibreOffice dependency because the wrappers can be regenerated from the UNO interfaces provided by the new LibreOffice version.

First build `loj-proxy`:

```bash id="rxjdfr"
cd loj-proxy
mvn clean package
```

Then move to the sample project:

```bash id="ghytnk"
cd ../loj-sb-sample
```

Generate the proxy classes using `proxy.properties`:

```bash id="lzbvwu"
java -jar ../loj-proxy/target/loj-proxy-1.0-SNAPSHOT.jar \
  loproxy proxy.properties
```

The arguments are:

```text id="mrczws"
java -jar loj-proxy.jar <output package/directory> <properties file>
```

For the sample project:

```text id="tdasjp"
output package/directory : loproxy
properties file          : proxy.properties
```

`ProxyCreator` reads `proxy.properties`, loads the specified UNO interfaces using Java Reflection, analyzes their inherited interfaces and methods, and generates the corresponding Java source files.

Conceptually:

```text id="kbxnxj"
proxy.properties
       |
       v
 Class.forName()
       |
       v
 Reflection
       |
       v
 UNO interface analysis
       |
       v
 template.txt
       |
       v
 P_Doc.java
 P_Sheet.java
 P_Range.java
 P_Cell.java
 ...
```

Therefore, after changing the LibreOffice version, the generated proxy classes can be recreated against the updated UNO API.

## Proxy generation

`loj-proxy` recursively examines the public UNO interfaces specified in `proxy.properties`.

Generated methods delegate operations to the appropriate UNO interface using `UnoRuntime.queryInterface()` internally.

This turns code conceptually similar to:

```java id="qocgbx"
XSpreadsheet sheet =
    UnoRuntime.queryInterface(
        XSpreadsheet.class,
        object
    );

sheet.getCellByPosition(0, 0);
```

into ordinary wrapper calls.

The generator also handles inherited UNO interfaces.

### Passing proxy objects

When a generated method expects an UNO interface and the supplied argument is another LOJ proxy, the underlying UNO object is automatically extracted.

This allows generated wrappers to be used naturally with each other without manually unwrapping the underlying UNO objects.

## Property access

LibreOffice UNO makes extensive use of `XPropertySet`.

When a generated proxy includes `XPropertySet`, LOJ provides the fluent `prop()` method.

For example:

```java id="bltfac"
range
    .prop("CellBackColor", color)
    .prop("CellStyle", "My Style");
```

instead of repeatedly calling:

```java id="zbxdfr"
range.setPropertyValue("CellBackColor", color);
range.setPropertyValue("CellStyle", "My Style");
```

This is especially useful for spreadsheet formatting.

### Cells

```java id="ohmtnb"
Sheet sheet = doc.getSheet(0);

Cell cell = sheet.getCell("A1");
```

Cells can also be manipulated using a small fluent API:

```java id="qtfukr"
Cell cell = sheet.getCell("A1");

cell.set("JAN")
    .right()
    .set("FEB")
    .right()
    .set("MAR");
```

### Ranges

```java id="viyjve"
Range range = sheet.getRange("A1:D10");

range.prop("CellBackColor", 0xAAAAAA);
```

Ranges can also be iterated horizontally or vertically.

```java id="vzoxhu"
for (Cell cell : range.getHoriIterator()) {
    // ...
}
```

or:

```java id="dxmtgb"
for (Cell cell : range.getVertIterator()) {
    // ...
}
```

## Sheets and documents

Higher-level wrappers provide operations such as:

```java id="jdqkmf"
Sheet sheet = doc.getSheet("Sheet1");
```

Sheets can be copied:

```java id="qtvhcs"
Sheet newSheet =
    doc.copySheet(sheet, "New Sheet");
```

and imported from another document:

```java id="psukyb"
Sheet imported =
    newDoc.importSheet(
        originalDoc,
        "Original",
        "Imported"
    );
```

## Charts

LOJ can manipulate LibreOffice charts through generated UNO proxy classes.

For example:

```java id="juhjlc"
P_TableCharts charts =
    new P_TableCharts(sheet.getCharts());

charts.addNewByName(
    "Example",
    rectangle,
    addresses,
    true,
    true
);
```

The resulting embedded chart can then be wrapped:

```java id="jgqmsq"
P_TableChart tableChart =
    new P_TableChart(
        charts.getByName("Example")
    );

P_Chart chart =
    new P_Chart(
        tableChart.getEmbeddedObject()
    );
```

Properties can be changed using `Prop`:

```java id="lwmmlz"
Prop.of(chart.getDiagram())
    .set("Dim3D", Boolean.TRUE);

Prop.of(chart.getTitle())
    .set("String", "The new title");
```

## Streams and document conversion

`loj-util` provides adapters between Java streams and LibreOffice UNO streams.

This allows LibreOffice documents to be loaded or exported without requiring ordinary filesystem-based input/output.

For example:

```java id="rkhbux"
doc.writeToStream(
    outputStream,
    "calc_pdf_Export"
);
```

This is useful when LibreOffice is used as a document-processing backend in a server application.

## LibreOffice UNO quirks

LibreOffice UNO has a few APIs whose values cannot always be passed directly from one method to another.

One example is restoring frozen panes when copying or importing a Calc sheet.

LOJ obtains the current frozen-pane position from `XViewSplitable`:

```java id="ahdqxl"
int splitCol = controller.getSplitColumn();
int splitRow = controller.getSplitRow();
```

and restores it using `XViewFreezable.freezeAtPosition()`:

```java id="oetyfk"
controller.freezeAtPosition(splitCol, splitRow);
```

However, `getSplitRow()` and `freezeAtPosition()` use different row-position semantics.

In practical tests with LibreOffice, passing the value returned by `getSplitRow()` directly to `freezeAtPosition()` moves the frozen row boundary down by one row.

For example:

```text id="hkwrlu"
Source:
    frozen = true
    column = 0
    row    = 2

Destination before freezeAtPosition():
    frozen = false
    column = 0
    row    = 0

Destination after freezeAtPosition(0, 2):
    frozen = true
    column = 0
    row    = 3
```

The same behavior was reproduced with another row position:

```text id="rzwyns"
Source:
    column = 1
    row    = 4

Destination after freezeAtPosition(1, 4):
    column = 1
    row    = 5
```

Column positions do not show the same behavior.

For example, freezing at C1 produced:

```text id="skpbrn"
Source:
    column = 2
    row    = 0

Destination after freezeAtPosition(2, 0):
    column = 2
    row    = 0
```

Therefore LOJ adjusts only the row value before restoring the frozen panes:

```java id="wceuwk"
// getSplitRow() and freezeAtPosition() use different row-position semantics.
// Subtract one to preserve the source sheet's frozen row position.
// No adjustment is required for getSplitColumn().
if (splitRow > 1) {
    splitRow--;
}

destController.freezeAtPosition(splitCol, splitRow);
```

This behavior is important when copying a sheet while preserving its view settings.

In short:

```text id="fjcvdi"
getSplitColumn()
        |
        +--------------------------+
                                   |
                                   v
                          freezeAtPosition()

getSplitRow()
        |
        v
   subtract 1
        |
        +--------------------------+
                                   |
                                   v
                          freezeAtPosition()
```

This adjustment is intentional and should not be removed as an apparent off-by-one error.

- Maven
- LibreOffice

## Build

Clone the repository:

```bash id="ybbppq"
git clone https://github.com/ns2j/loj.git
cd loj
```

Build the project:

```bash id="vfvcng"
mvn clean package
```

## Updating the LibreOffice version

When updating the LibreOffice dependency:

1. Change the LibreOffice version in the Maven configuration.
2. Rebuild `loj-proxy`.
3. Regenerate the `loproxy` classes.
4. Rebuild and test the sample application.

For example:

```bash id="oyvcoj"
mvn clean package

cd loj-sb-sample

java -jar ../loj-proxy/target/loj-proxy-1.0-SNAPSHOT.jar \
  loproxy proxy.properties

cd ..

mvn clean package
```

Regenerating the proxies ensures that the generated Java wrappers reflect the UNO interfaces of the LibreOffice version currently used by the project.

## Design philosophy

The LibreOffice UNO API is powerful and flexible, but its generic interface-oriented architecture can result in verbose Java code.

LOJ separates the problem into two layers:

```text id="ddqgpy"
LibreOffice UNO
       |
       | generated automatically
       v
Generated P_* classes
       |
       | extended manually
       v
Doc / Sheet / Range / Cell
       |
       v
Application code
```

The proxy generator handles the mechanical parts of UNO interface delegation.

The higher-level classes provide APIs that are easier to read and write.

In other words, LOJ does not try to replace UNO.

Its goal is to make LibreOffice UNO programming feel more like ordinary Java programming.
